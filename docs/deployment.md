# Промышленный запуск

Когда читать: ставите шлюз «насовсем» — опубликованное приложение, которое поднимается само и
переживает перезагрузку, а не `dotnet run` из папки проекта.

Команды даны двумя блоками: первый — PowerShell, второй — bash (Git Bash на Windows, обычный
терминал на macOS и Linux). Один блок значит, что команда одинакова в обеих оболочках.

Три способа запуска:

| | `dotnet run` | Установка на машину | Docker |
|---|---|---|---|
| Для чего | разработка | постоянная работа на своём ПК | изоляция, а также macOS и Linux |
| Что запускается | сборка `Debug` | опубликованный exe, `Release` | контейнер |
| Автозапуск | нет | задача Планировщика при входе | `restart: unless-stopped` |
| Секреты | открытым текстом рядом с проектом | DPAPI в папке данных | переменные окружения |
| Что видит агент | всю машину | всю машину | только смонтированные тома |

## Установка на машину

### Из готового архива

На странице [Releases](https://github.com/aRRma/AgentsTracker/releases) к каждой версии
приложены два архива под Windows x64: `…-win-x64-self-contained.zip` со средой выполнения
внутри (не нужен ни SDK, ни Runtime) и `…-win-x64.zip` поменьше, которому нужен
**ASP.NET Core Runtime 10**. Шлюз собран Web SDK и просит два фреймворка,
`Microsoft.NETCore.App` и `Microsoft.AspNetCore.App`, поэтому обычного .NET Runtime не хватит.
Внутри тот же результат `dotnet publish`: скопируйте `appsettings.Local.example.json` рядом с
exe как `appsettings.Local.json`, заполните его и выполните `install --start`.

Раскладка архива: папка `AgentsTracker-<тег>-win-x64` (или `…-win-x64-self-contained`, имя то же,
что у архива) с приложением и рядом с ней `install.txt` — короткая инструкция для пользователя
(исходник — `docs/install-quickstart.txt`) — и `claude-settings.example.json`, правила разрешений
агента для `~/.claude/settings.json` ([claude-permissions.md](claude-permissions.md),
«Перенос на другой ПК»). Папка не даёт распаковке «сюда» рассыпать полторы сотни файлов по папке
загрузок, а её имя показывает установленную версию.

### Из исходников

Публикация и регистрация автозапуска — две команды, скриптов не нужно:

```
dotnet publish src/AgentsTracker.Gateway -c Release -o C:/Apps/AgentsTracker
C:/Apps/AgentsTracker/AgentsTracker.Gateway.exe install --start
```

Папку установки берите вне исходников шлюза, иначе `git clean` снесёт её вместе с приложением.
Чтобы среда выполнения была внутри (на машине не нужен .NET), добавьте к публикации
`-r win-x64 --self-contained`.

`install` регистрирует **тот exe, который его запустил**, там, где он лежит. Поэтому годится и
публикация с этой машины, и папка с другой: во втором случае не нужны ни исходники, ни SDK. Под
`dotnet run` и внутри контейнера команда отказывается, а exe из папки сборки `bin` — предупреждает.
Заодно команда:

- переносит `appsettings.Local.json` из-под exe в папку данных и шифрует секреты канала
  (`Channel:Settings:BotToken`) и `Proxy`, как `protect-secrets`. Если в папке данных конфиг
  уже есть, остаётся он, а копия рядом с exe удаляется непрочитанной (`dotnet publish` копирует
  туда файл с открытым токеном). Конфиг со старым `Gateway:BotToken` отвергается и автозапуск
  не регистрируется — сначала `scripts\migrate-channel-settings.ps1` (`-Path` для файла рядом с exe);
- закрывает папку данных правами: владелец и SYSTEM;
- перезаписывает задачу с тем же именем;
- печатает итог: путь, папку данных, порты, заполнен ли конфиг.

Ключи: `--start` запускает сразу, `--name <имя>` меняет имя записи автозапуска (по умолчанию
`AgentsTracker Gateway`).

`uninstall` (тот же `--name`) останавливает шлюз, в том числе поднятый руками из того же пути
exe, и снимает автозапуск. Данные не трогает. Он освобождает файлы перед новой публикацией.

Задача создаётся **от вашей учётной записи и без повышения прав**. Службой ставить нельзя: Claude
Code читает OAuth-логин из `%USERPROFILE%\.claude`, под SYSTEM его там нет. Поэтому шлюз работает,
пока вы вошли в Windows. Нужна работа без входа в сессию — включите автовход и блокируйте экран,
а не переводите задачу на SYSTEM.

На macOS и Linux `install` пока отказывается: там нужны агент launchd и пользовательский юнит
systemd, они появятся отдельно. До тех пор там остаётся Docker.

### Обновление версии

1. Сначала выполните `AgentsTracker.Gateway.exe uninstall`: пока exe запущен, публикация поверх
   падает с `MSB3021`, а задача осталась бы на старой версии.
2. Из исходников: `git pull` и та же `dotnet publish`, что выше. Из архива: новая папка на место
   старой.
3. Выполните `AgentsTracker.Gateway.exe install --start`.

Конфиг, сессии и журнал в папке данных остаются. Если обновление пришлось на работающую задачу, в
её чат уйдёт «⚠️ Предыдущий запуск прерван перезапуском шлюза» с подсказкой написать «продолжай»;
прерванный вопрос задают заново через `/ask`.

### Проверка после установки

```powershell
Get-ScheduledTaskInfo -TaskName 'AgentsTracker Gateway' | Select-Object LastRunTime, LastTaskResult
Get-Process AgentsTracker.Gateway | Select-Object Id, Path
Invoke-RestMethod http://127.0.0.1:5100/api/snapshot | Select-Object version, agent, cliVersion
```

```bash
schtasks //Query //TN "AgentsTracker Gateway" //FO LIST
tasklist //FI "IMAGENAME eq AgentsTracker.Gateway.exe"
curl -s http://127.0.0.1:5100/api/snapshot
```

`LastTaskResult` = 0 и процесс с путём из папки установки значат, что задача поднялась, и в
Telegram придёт «🔌 Шлюз запущен» с версией. Поле `version` снимка и версия в сообщении — одна
строка: после обновления по ней видно, что работает новая сборка, а не старая задача.

Код выхода 1 шлюз возвращает намеренно, когда не может стартовать: конфиг не прошёл проверку или
Telegram шесть раз подряд (с интервалом 10 с) отверг токен. Тогда Планировщик перезапускает задачу
(3 попытки с интервалом в минуту). Отсутствие сети поводом для выхода не служит: шлюз ждёт между
попытками 10 с, 20 с… до 5 мин, сколько понадобится.

## Конфиг и секреты

Боевой конфиг — единственный файл **вне** папки установки:

```
%LOCALAPPDATA%\AgentsTracker\appsettings.Local.json
```

Так папку установки можно удалять и пересоздавать, не трогая токен, сессии и журнал.
Перешифровать после правки — `AgentsTracker.Gateway.exe protect-secrets [файл]`. Команда шифрует
на месте `Proxy` и секреты канала (`BotToken`, собственный `Proxy` канала). Без файла берёт
конфиг из папки данных, иначе лежащий рядом с exe, и переносит результат в папку данных.
Конфиг, который уже лежит в папке данных, она не перезапишет и откажется от конфига со старыми
ключами `Gateway:BotToken`/`Gateway:AllowedUserIds` (`scripts\migrate-channel-settings.ps1`).

DPAPI расшифровывает только **та же учётная запись на той же машине**. Конфиг с `dpapi:…` не
переносится на другой ПК и не годится другому пользователю: на новой машине положите файл с
открытыми значениями и выполните `protect-secrets` там. При сбросе пароля учётной записи (не
смене) DPAPI-ключ теряется, шлюз упадёт на старте с понятной причиной — впишите значения заново и
повторите. Вне Windows `protect-secrets` откажется: DPAPI там нет, секреты держат в переменных
окружения.

Слои конфига, каждый следующий перекрывает предыдущий:

1. `appsettings.json` рядом с exe — дефолты, в репозитории, секретов нет;
2. `appsettings.Local.json` рядом с exe — только для отладки из IDE, при установке переносится в папку данных, а если там конфиг уже есть, удаляется;
3. `appsettings.Local.json` в папке данных — боевой;
4. переменные окружения `Gateway__Ключ` (вложенные — `Gateway__Claude__Executable`).

Конфиг читается **один раз на старте**: поправили — перезапустите.

Папка данных — `%LOCALAPPDATA%\AgentsTracker` (на Linux и macOS `~/.local/share/AgentsTracker`),
переносит её `Gateway:DataDirectory`. В папке лежит сам файл конфига, поэтому этот ключ читается
раньше остального: только из `appsettings.json` рядом с exe или из переменной
`Gateway__DataDirectory`.

## Порты

| Ключ | По умолчанию | Что это |
|---|---|---|
| `McpPort` | 5099 | по нему `claude` спрашивает у шлюза разрешения. Всегда только `127.0.0.1`, закрыт токеном в заголовке. Выключить нельзя — без него не будет кнопок |
| `MonitorPort` | 5100 | веб-монитор. `0` выключает. Совпадение с `McpPort` отвергает проверка на старте |
| `MonitorBind` | `loopback` | где слушать монитор. `any` нужен в контейнере, на обычной машине оставьте `loopback` |

```json
{ "Gateway": { "McpPort": 15099, "MonitorPort": 15100 } }
```

Порты слушает Kestrel явными `Listen`, поэтому `--urls` и `ASPNETCORE_URLS` игнорируются — порты
задают только эти ключи. Секция `Kestrel:Endpoints` их тоже не переносит: ASP.NET Core добавляет
такие адреса к `Listen`, и она лишь откроет лишний порт. Не используйте её. «Любой свободный» порт
тоже нельзя: номер MCP-порта попадает в конфигурацию для CLI и должен быть фиксированным.

Если порт занят другим приложением, на старте будет `Failed to bind to address`, и шлюз не
поднимется:

```powershell
Get-NetTCPConnection -LocalPort 5099,5100 -State Listen -ErrorAction SilentlyContinue |
    Select-Object LocalPort, OwningProcess
```

```bash
netstat -ano | grep -E ':(5099|5100)\s.*LISTENING'
```

Правила брандмауэра не нужны: при `MonitorBind: loopback` наружу порты не смотрят.

## Docker

Контейнер даёт то, чего нет в установке на машину: агент видит только смонтированные тома.
Неудачная команда и кнопка «Всегда» не дотягиваются до остальной системы.

Скопируйте `.env.example` в `.env` и впишите токен, свой id и папку с проектами. Затем:

```
docker compose up -d --build
docker compose exec gateway claude      # один раз войти в аккаунт агента
```

Вход в аккаунт живёт в томе `claude-home`, состояние шлюза — в томе `data`. Хостовый `~/.claude`
намеренно не пробрасывается: контейнер и рабочая машина не должны делить настройки, плагины и
историю сессий.

- **Секреты — переменные окружения.** DPAPI на Linux нет, поэтому
  `Gateway__Channel__Settings__BotToken` и `Gateway__Channel__Settings__AllowedUserIds__0` живут
  в `.env`, а он в `.gitignore`.
- **Монитор.** В контейнере он слушает `0.0.0.0` (`Gateway__MonitorBind=any` задан в образе),
  иначе опубликовать порт было бы нечем. Наружу он идёт как `127.0.0.1:5100:5100`: у страницы нет
  пароля, дальше своей машины её выпускать нельзя.
- **Пути проектов другие.** Внутри это `/projects/<проект>` (проект по умолчанию задаёт `PROJECT`
  в `.env`, а `Gateway__ProjectsRoot=/projects` из образа наполняет меню проектов). Сессии
  ключуются нормализованным путём, поэтому история сессий с хоста не подхватится.
- **Инструменты.** Агент умеет то, что стоит в образе: git, ripgrep и .NET SDK. Для других языков
  добавьте слой в `Dockerfile`.
- **Автозапуск** — `restart: unless-stopped`; `install` внутри контейнера отказывается и
  объясняет почему.
- **`init: true`** ставит перед шлюзом крошечный init. Шлюз как PID 1 должен был бы подбирать
  осиротевших потомков агента (фоновый dev-сервер после конца запуска) и не делает этого, они
  копились бы зомби. Из своего compose-файла не убирайте.

Обновление: `docker compose up -d --build`. Тома переживают пересборку.

## Данные, логи, резервная копия

Папка данных — всё состояние шлюза. На Windows открыть её могут только владелец и SYSTEM (в
контейнере это том `data`):

| Файл | Что |
|---|---|
| `appsettings.Local.json` | конфиг; на Windows секреты зашифрованы |
| `state.json` | сессии по проектам, выбор проекта, модели, режима и effort, версии, которыми ответили алиасы моделей, правила «Всегда» и доверенные проекты по проектам, статистика, история запусков |
| `audit\audit-ГГГГ-ММ.jsonl` | журнал «кто, что, когда», по файлу на месяц |
| `inbox\<чат>\<проект>\` | картинки из чата; чистятся через `Attachments:RetentionHours` (по умолчанию 24) |
| `mcp-gateway-<pid>-<запуск>.json` | временный, по одному на запуск агента: создаётся при его старте, удаляется в конце |

В резервную копию кладите `state.json` и `audit\`. Конфиг — только если помните, что `dpapi:…`
восстановится лишь на этой машине под этой учётной записью.

Файла лога нет. Задача Планировщика пишет в консоль, которой нет: смотрите лог в мониторе (раздел
«Лог») или `GET /api/log?count=&level=`. В контейнере — `docker compose logs -f`.

## Несколько экземпляров

Под одной учётной записью — **один шлюз**: папка данных общая, а бот в Telegram отдаёт
`getUpdates` только одному процессу (второй получает 409). Несколько ботов сразу — это разные
пользователи Windows или разные контейнеры, у каждого свой том и свой `~/.claude`. Порты тогда
разведите: loopback общий на всю машину. Временный второй экземпляр при отладке — `operations.md`.

## Выпуск релиза

Релиз собирает GitHub Actions по пушу тега `v*` — `.github/workflows/release.yml`:

```powershell
git tag v0.1.0
git push origin v0.1.0
```

Сборка публикует оба архива win-x64 (`AgentsTracker-<тег>-win-x64-self-contained.zip` со средой
выполнения, `AgentsTracker-<тег>-win-x64.zip` без неё) и создаёт релиз. Заметки берутся из
`docs/release-notes/<тег>.md`, поэтому файл заводят **до** пуша тега; нет файла — GitHub соберёт
список коммитов.

Заметки пишут **коротко и человеческим языком**, со стороны того, кто пользуется ботом: одна-две
фразы о том, что изменилось, затем список «Что нового», по пункту на видимое изменение. Без
рассуждений, имён классов, флагов и невидимых изменений. Разделы про установку и обновление —
шаблон: копируются из прошлого выпуска, меняется только версия.

Номер тега без `v` уходит в `-p:Version`; в csproj стоит `0.0.0-dev`, и сборка из исходников этой
пометкой отличается от выпущенной. Тот же номер шлюз печатает в лог первой строкой, кладёт в
`version` снимка монитора и в сообщение «🔌 Шлюз запущен».

Упаковка собирает раскладку архива, описанную выше; `claude-settings.example.json` берётся из
`docs/examples/`. `install.txt` в UTF-8 с BOM, иначе кириллица в Блокноте старых сборок Windows
превращается в кракозябры. Токенов заводить не нужно: workflow ходит встроенным `github.token` с
правом `contents: write`. Перед упаковкой он удаляет из публикации `appsettings.Local.json` и
`appsettings.Development.json`, чтобы открытый токен не попал в архив релиза ни при каких условиях.
