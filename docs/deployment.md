# Промышленный запуск

Когда читать: ставите шлюз «насовсем» — не `dotnet run` из папки проекта, а опубликованный
exe, который сам поднимается при входе в Windows и переживает перезагрузку.

Отличия от запуска из репозитория:

| | Из репозитория | Промышленно |
|---|---|---|
| Что запускается | `dotnet run`, сборка `Debug` | опубликованный exe, `Release` |
| Откуда | `src\AgentsTracker.Gateway\bin\Debug\net10.0` | папка установки вне репозитория |
| Конфиг | `appsettings.Local.json` рядом с проектом, секреты открытым текстом | `%LOCALAPPDATA%\AgentsTracker\appsettings.Local.json`, `BotToken` и `Proxy` под DPAPI |
| Кто запускает | вы руками | задача Планировщика при входе в Windows |
| Обновление | пересборка | остановить задачу → публикация → запустить |

## Шаг 1. Публикация и установка

Всё делает один скрипт: публикует, чистит секреты из папки публикации, шифрует конфиг,
закрывает ACL папки данных и регистрирует задачу Планировщика.

```powershell
pwsh -File scripts\install-autostart.ps1 -InstallDir C:\Apps\AgentsTracker
```

Параметры:

| Параметр | Зачем |
|---|---|
| `-InstallDir <путь>` | куда публиковать и откуда запускать. По умолчанию `publish\` в репозитории — для постоянной работы возьмите папку вне репозитория, иначе `git clean` снесёт установку |
| `-SelfContained` | публикация вместе со средой выполнения (`win-x64`): на машине не нужен .NET. Папка тяжелее (~70 МБ), обновления безопасности .NET придётся накатывать пересборкой |
| `-SkipPublish` | не собирать: в `-InstallDir` уже лежит готовая публикация. Так ставят на машину без исходников и без SDK |
| `-TaskName <имя>` | имя задачи Планировщика, по умолчанию `AgentsTracker Gateway` |
| `-Uninstall` | снять задачу. Папку установки и данные не трогает |

Скрипт сам останавливает шлюз, запущенный из папки установки: иначе `dotnet publish` упал бы
с `MSB3021` (exe занят), а задача осталась бы на старой версии.

Задача создаётся **от вашей учётной записи и без повышения прав**. Службой ставить нельзя:
Claude Code читает OAuth-логин из `%USERPROFILE%\.claude`, под SYSTEM его там нет.
Следствие — шлюз работает, пока вы вошли в Windows. Нужна работа без входа в сессию —
включите автовход и блокируйте экран, а не переводите задачу на SYSTEM.

## Шаг 2. Конфиг и секреты

Боевой конфиг — единственный файл, и лежит он **вне** папки установки:

```
%LOCALAPPDATA%\AgentsTracker\appsettings.Local.json
```

Так папку установки можно удалять и пересоздавать, не трогая токен, сессии и аудит.
Скрипт при первой установке перенесёт туда `appsettings.Local.json` из папки проекта (или
положенный рядом с exe) и зашифрует `BotToken` и `Proxy` — в файле они станут `dpapi:…`.
Позже — вручную:

```powershell
C:\Apps\AgentsTracker\AgentsTracker.Gateway.exe protect-secrets
```

Про DPAPI важно: расшифровать может только **та же учётная запись на той же машине**.
Поэтому конфиг с зашифрованными значениями не переносится на другой ПК и не годится другому
пользователю — на новой машине положите файл с открытыми значениями и выполните
`protect-secrets` там. При смене пароля учётной записи через сброс (не смену) DPAPI-ключ
теряется, шлюз упадёт на старте с сообщением про другую учётную запись — впишите значения
заново открытым текстом и повторите `protect-secrets`.

Слои конфига, каждый следующий перекрывает предыдущий:

1. `appsettings.json` рядом с exe — дефолты, в репозитории, секретов нет;
2. `appsettings.Local.json` рядом с exe — только для отладки из IDE, в боевой папке скрипт
   его удаляет;
3. `appsettings.Local.json` в папке данных — боевой;
4. переменные окружения `Gateway__Ключ` (вложенные — `Gateway__Claude__Executable`).

Конфиг читается **один раз на старте**, слежения за файлом нет: поправили — перезапустите
задачу.

## Шаг 3. Порты

Два порта, оба только на `127.0.0.1`, задаются в секции `Gateway`:

| Ключ | По умолчанию | Что это |
|---|---|---|
| `McpPort` | 5099 | по нему `claude` спрашивает у шлюза разрешения. Закрыт токеном в заголовке. Выключить нельзя — без него не будет кнопок |
| `MonitorPort` | 5100 | веб-монитор. `0` выключает. Совпасть с `McpPort` не даст проверка на старте |

```json
{ "Gateway": { "McpPort": 15099, "MonitorPort": 15100 } }
```

Порты слушает Kestrel явными `Listen`, поэтому `--urls`, `ASPNETCORE_URLS` и секция
`Kestrel` в конфиге на них **не влияют** — только эти два ключа. Выбрать порт «любой
свободный» тоже нельзя: номер MCP-порта попадает в файл конфигурации для CLI, он должен быть
фиксированным.

Когда менять: порт уже занят другим приложением — на старте будет
`Failed to bind to address http://127.0.0.1:5100` и шлюз не поднимется. Занятость проверяется
так:

```powershell
Get-NetTCPConnection -LocalPort 5099,5100 -State Listen -ErrorAction SilentlyContinue |
    Select-Object LocalPort, OwningProcess
```

Правила брандмауэра не нужны: наружу порты не смотрят.

## Шаг 4. Проверка после установки

```powershell
Start-ScheduledTask -TaskName 'AgentsTracker Gateway'
Get-ScheduledTaskInfo -TaskName 'AgentsTracker Gateway' | Select-Object LastRunTime, LastTaskResult
Get-Process AgentsTracker.Gateway | Select-Object Id, Path
Invoke-RestMethod http://127.0.0.1:5100/api/snapshot | Select-Object agent, cliVersion
```

`LastTaskResult` = 0 и процесс с путём из папки установки — задача поднялась. В Telegram
придёт «🔌 Шлюз запущен». Ненулевой код выхода шлюз возвращает намеренно, когда не смог
подключиться к Telegram: по нему Планировщик перезапускает задачу (3 попытки с интервалом в
минуту).

## Обновление версии

```powershell
git pull
pwsh -File scripts\install-autostart.ps1 -InstallDir C:\Apps\AgentsTracker
Start-ScheduledTask -TaskName 'AgentsTracker Gateway'
```

Скрипт остановит работающий шлюз, опубликует поверх и перерегистрирует задачу. Конфиг,
сессии и аудит в папке данных не затрагиваются. Если обновление пришлось на работающую
задачу, в её чат уйдёт «прервана, напишите „продолжай“».

Перенос готовой публикации на другую машину: скопируйте папку установки и
`scripts\install-autostart.ps1`, там запустите с `-SkipPublish`, конфиг заполните на месте
(DPAPI, см. выше).

## Данные, логи, резервная копия

`%LOCALAPPDATA%\AgentsTracker\` — всё состояние шлюза, доступ только у владельца и SYSTEM:

| Файл | Что |
|---|---|
| `appsettings.Local.json` | конфиг с зашифрованными секретами |
| `state.json` | сессии по проектам, выбор модели и режима, правила «Всегда», история запусков |
| `audit\audit-ГГГГ-ММ.jsonl` | журнал «кто, что, когда», по файлу на месяц |
| `mcp-gateway-<pid>.json` | временный, создаётся на запуск и удаляется при остановке |

В резервную копию имеет смысл класть `state.json` и `audit\`. Конфиг — только если помните,
что `dpapi:…` восстановится лишь на этой же машине под этой же учётной записью.

Файла лога нет: запущенная Планировщиком задача пишет в консоль, которой нет. Смотрите лог в
мониторе (раздел «Лог», кольцевой буфер последних записей) или `GET /api/log?count=&level=`.
Нужен лог на диск — запускайте exe не напрямую, а через обёртку с перенаправлением вывода.

## Несколько экземпляров

Под одной учётной записью — **один шлюз**: `state.json` в папке данных общий, а один бот в
Telegram отдаёт `getUpdates` только одному процессу (второй получает 409). Разные боты и
разные проекты одновременно — только под разными пользователями Windows: у каждого свой
`%LOCALAPPDATA%`, своя папка данных и свой `~/.claude`. Порты при этом всё равно разведите:
loopback общий на всю машину.

Временная проба второго экземпляра при отладке — `operations.md`.
