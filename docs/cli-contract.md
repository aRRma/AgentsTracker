# Контракт с Claude Code CLI

Когда читать: правите `ClaudeBackend`, `ClaudePermissionTool`, `ClaudeLimits`, работу с
сессиями или обновили CLI. Схема не задокументирована — всё ниже проверено на живом CLI 2.1.x.

## Подтверждения (MCP-инструмент `mcp__tg__approve`)

CLI зовёт инструмент с `{"tool_name":…,"input":{…},"tool_use_id":…}`. Ответ — JSON-строка:

- `{"behavior":"allow","updatedInput":{…}}` — `updatedInput` **обязателен**, без него CLI
  отклоняет вызов;
- `{"behavior":"deny","message":"…"}`.

`ClaudePermissionTool` читает поля защитно (`Read(...)` перебирает snake_case/camelCase). Сырой
payload логируется только на Debug: на Information для Edit/Write это содержимое файлов.

`AskUserQuestion` приходит в тот же инструмент и требует `updatedInput` с исходным `questions`
и `answers` (ключ — текст вопроса); в хост уходит как `IOperatorConsole.AskAsync`.

У CLI 2.1.261 разошлась справка, а не флаги: `--help` показывает `default` как `manual` (CLI
по-прежнему принимает `default` — `manual` лишь алиас) и больше не перечисляет
`--permission-prompt-tool` отдельно (только внутри `--permission-prompts`), но флаг работает.
После обновления CLI проверить оба.

### Кнопка «Всегда»

Двояка:

- CLI прислал `permission_suggestions` с `destination: localSettings`, `type: addRules`,
  `behavior: allow` — правило пишет **сам CLI** в `.claude/settings.local.json` проекта (обычно
  префиксное). Карточка показывает именно его, в хост оно приходит как `PersistentRule.Raw` и
  возвращается без изменений в `updatedPermissions`. Назад уходят только правила, которые
  карточка показала (`ApprovalCardRenderer.ShownRules`, не больше 4): у составной команды
  предложение на каждую часть, и остальные записались бы невидимыми. Предложения других видов
  (`setMode`, `addDirectories`) отбрасываются — карточке их не показать.
- Иначе шлюз запоминает точную сигнатуру в `state.json` (`AlwaysAllowByProject`, ключ —
  нормализованный путь проекта), видно в `/rules`. Правила шлюза действуют только в своём
  проекте: `git push --force` из одного проекта не должен молча проходить в остальных. Проект —
  **запуска** (`RunScope.ProjectPath`), а не текущий в чате: `/project`, сменённый посреди задачи,
  иначе одолжил бы ей правила другого проекта и унёс бы туда её «Всегда».

### Невидимый хвост

Одобрять команду, которую не видно целиком, нельзя. Когда `ApprovalCard` что-то обрезал
(команда, стороны правки, остальные правки `MultiEdit`, хвост `Write`), `OperatorConsole`
перед карточкой шлёт полный текст файлом (`ApprovalBroker.SendAttachmentAsync`), карточка
предупреждает «показано не всё». Имя и содержимое файла решает `ApprovalCardRenderer`
(`ApprovalAttachment`): обычно `<инструмент>-input.txt`, где каждое обрезанное поле идёт под своим заголовком
«=== <поле> ===» («=== Команда ===», «=== Было ===» / «=== Станет ===», «=== Вход целиком ===»), план
`ExitPlanMode` — целиком как `plan.md` (`Truncated.AddDocument`). Карточки собираются через
`EscapeCapped` с лимитом на каждый фрагмент: переполненное сообщение упало бы при отправке, а
исключение стало бы отказом.

### Самовыдача прав

Проверено на CLI 2.1.x: `Write` в `.claude/settings.local.json` отклоняется даже в
`acceptEdits` (виден в `permission_denials`). После обновления CLI перепроверить тем же
запуском во временной папке:

```powershell
claude -p "…" --permission-mode acceptEdits --output-format json
```

### Настройки проекта и диалог доверия

`-p` пропускает диалог доверия к папке (так сказано в `claude --help`): `.claude/settings.json`
проекта читается сразу. Проверено на CLI 2.1.292 временной папкой с хуком `SessionStart` — хук
выполнился при `--permission-mode default` без единого вопроса; тот же запуск в папке без настроек
— нет. Значит, склонированный чужой проект запустил бы свои хуки и MCP-серверы без карточки
подтверждения. `--permission-mode`, переданный явно, всё равно перекрывает `defaultMode`
проекта.

Поэтому спрашивает хост, до запуска: `IAgentBackend.InspectProject` (у Claude —
`ClaudeProjectSettings`) перечисляет хуки, правила `allow`, MCP-серверы, ключи-команды
(`apiKeyHelper`, `statusLine`…), имена `env`, плагины и файлы `.claude/{skills,commands,agents,hooks}`
и отдаёт SHA-256-отпечаток их всех; `ProjectTrustGate` показывает карточку «Доверять проекту?» и
хранит отпечаток в `GatewayState.TrustedProjects`. Любая правка этих файлов меняет отпечаток, и
карточка приходит снова. Вопрос не проверяется: он идёт в пустой временной папке, которая
пересоздаётся перед каждым вопросом — иначе агент задачи мог бы положить туда `.claude/settings.json`,
и его хук выполнялся бы на каждом `/ask`; не очистившаяся папка — отказ в вопросе.

Что держит отпечаток честным: файлы настроек разбираются всегда (до 16 МБ — раздутый пробелами
`settings.json` не должен прятать хук; больше — пункт «проверьте вручную»); хуки, ключи-команды,
MCP-серверы и переменные `env` (со значением под маской: `NODE_OPTIONS=--require` выполняет код) идут
на карточке первыми, а правила `allow` сворачиваются в одну строку, чтобы хук не ушёл в «и ещё N»;
в отпечаток идут все файлы, правила `allow` из `settings.local.json` и `node_modules`/`.pyc`/`.log`
тоже — пропущенное по имени можно было бы менять после доверия, — ценой лишней карточки после
«Всегда» с правилом агента; ссылка на папку не обходится, но становится пунктом; у каждой папки свой
предел в 2000 файлов. После «Доверять» проект проверяется ещё раз: если файлы сменились, пока
карточка ждала, приходит новая карточка с новым списком. «Отклонить» и молчание снимают очередь
задач, как отказ по лимиту, — иначе каждая задача из очереди ждала бы свою карточку. После
обновления CLI пропуск доверия перепроверить тем же запуском во временной папке.

### Ожидание ответа

`ApprovalBroker` держит вызов MCP на `TaskCompletionSource` до нажатия и возвращает
`ChoiceResult` (ключ + кто нажал). `WaitAsync` различает таймаут и отмену: `/stop` должен
бросать `OperationCanceledException`, а не выглядеть как «не ответил вовремя».

Таймауты шлюза: `ApprovalTimeoutMinutes` (15) — карточка, `RunTimeoutMinutes` (60) — весь
`claude -p`; оба 1..1440.

Таймаут и `/stop` убивают процесс вместе с его сабагентами — они работают внутри него. Остаются:
правки на диске, сессия (следующее сообщение её продолжит) и все шаги сабагентов — CLI пишет их по
ходу в `~/.claude/projects/<проект>/<сессия>/subagents/agent-*.jsonl`. Теряется итоговый отчёт
сабагента основному агенту. Поэтому сообщение о прерванной задаче советует написать «продолжи», а
если в запуске работали сабагенты (был вложенный вызов инструмента) — попросить агента прочитать их
шаги: `ClaudeBackend.Resumable`.

У CLI поверх этого свой предел на вызов MCP-инструмента: по умолчанию он обрывает вызов, если
сервер молчит 5 минут (`CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`, ошибка «sent no response or
progress for 300s»). Карточка в чате при этом ещё висит, а агент уже получил отказ. Поэтому
`McpConfigFile` пишет серверу `timeout` = `ApprovalTimeoutMinutes` + 1 мин: это и предел
вызова, и (с CLI 2.1.203) нижняя граница порога простоя. Progress-уведомления его не
продлевают — слать их незачем. На CLI старше 2.1.203 порог остаётся 5 минут, дольше карточка
не живёт.

## Файл в чат (MCP-инструмент `mcp__tg__send_file`)

Второй инструмент того же сервера `tg`, зовёт его сам агент (`ClaudeSendFileTool`).
Аргументы: `path` (абсолютный или от папки проекта), `caption` (подпись, без разметки),
`as_document` (картинку документом, без сжатия). Ответ — JSON-строка `{"sent":true}` или
`{"sent":false,"reason":"…"}`; отказ всегда ответом: ошибка инструмента у CLI выглядит как
сбой сервера, и агент не понимает, что не так.

Политика — в `OperatorConsole.SendFileAsync`, инструмент только переводит: файл должен лежать
в папке текущего проекта (`ProjectCatalog.Normalize` с обеих сторон, `ProjectCatalog.IsInside`),
папка данных шлюза запрещена отдельно; ни сам файл, ни папки между ним и корнем проекта не
должны быть символической ссылкой или junction — путь проверяется как строка, а открывает файл
ОС по ссылкам, и ссылка внутри проекта наружу отдала бы чужой файл; расширение из белого списка в коде
(`.md .txt .json .cs .js .html .zip .7z` — документом, `.png .jpg .jpeg` — фото; содержимое
архива не разбирается, и проверки пути относятся только к самому архиву — внутри может уехать
что угодно, до чего дотянулся агент, включая файлы вне проекта); размер и подпись —
по `ChannelLimits` канала. Отказы тоже идут в аудит `file.send` с исходом `refused`.

Инструмент передаётся в `--allowedTools mcp__tg__send_file`, чтобы CLI не звал
`mcp__tg__approve` на каждую отправку: папку, тип и размер шлюз проверяет сам. Проверено на
CLI 2.1.261 пробным экземпляром: `tools/list` отдаёт оба инструмента, `claude -p` с этим
флагом зовёт `send_file` сразу, `approve` не трогает (`permission_denials` пуст). После
обновления CLI перепроверить тем же способом: карточка на `tg:send_file` — значит флаг
перестал действовать.

## Картинка из чата (`--add-dir`)

Пользователь может прислать боту картинку. Шлюз скачивает её (`AttachmentInbox`), кладёт
абсолютный путь в промпт и открывает агенту папку через `--add-dir`; увидит картинку агент
только когда сам позовёт на этот путь `Read` — поэтому в промпте написано, что с ней делать,
а не просто путь.

Раскладка: `<папка данных>\inbox\<чат>\<проект>\`. В `--add-dir` уходит папка **чата**, а не
папка данных (там `state.json`, `appsettings.Local.json` с секретами и токен MCP) и не подпапка
проекта: пока сообщение ждало очереди, `/project` мог смениться, а путь в промпте уже записан.
Подпапка проекта нужна, чтобы `/new` в одном проекте не стирал картинки другого.

Политика — зеркало `OperatorConsole.SendFileAsync` для входящего направления: только PNG и
JPEG, причём тип определяется по **сигнатуре байт**, а не по MIME и имени файла — и то, и
другое пишет отправитель (`.png` с текстом внутри отклоняется). Имя файла придумывает шлюз
(`<метка времени>-<8 hex>.<ext>`); имя от Telegram не используется нигде — в нём может быть
`..\` или зарезервированное имя устройства. Размер ограничен `Gateway:Attachments:MaxBytes` и
каналом (`ChannelLimits.AttachmentBytes` — Telegram отдаёт боту не больше 20 МБ): заявленный
проверяется до скачивания, фактический — по ходу. Всё остальное — голос, видео, документ не с
картинкой — получает вежливый отказ и до очереди агента не доходит. И принятый файл, и каждый
отказ идут в аудит `file.receive`.

Чистка: всё старше `RetentionHours` (24) убирается при старте шлюза и перед каждым новым
вложением, а подпапка проекта удаляется при закрытии сессии (`/new`, кнопка «Новая», потерянная
CLI сессия). Папка одна на проект, а не на сессию: `/new` уносит и картинки других сессий того
же проекта — тех, на которые можно вернуться через `/sessions`. Поэтому картинка может исчезнуть
к моменту, когда агент решит перечитать её: он получит ошибку чтения и скажет об этом.

Проверено на CLI 2.1.261: `claude -p … --add-dir <папка> --permission-mode default` читает PNG
из этой папки **без** карточки `mcp__tg__approve` (`permission_denials` пуст) и описывает её
верно. После обновления CLI перепроверить тем же способом. Вырожденная картинка (собранный
руками PNG на 116 байт) вернулась как «media removed — rejected by API»: настоящие скриншоты
проходят, а искусственный в тесте может и не пройти.

## Запуск и поток событий

CLI запускается с `--output-format stream-json --verbose` (без `--verbose` поток в `-p` не
пишется). `ClaudeBackend.StreamCollector` разбирает stdout построчно
(`ClaudeStreamEvent.Classify`): вызовы инструментов → `IAgentRunObserver.Activity`, остальное
отбрасывается — в долгом запуске это мегабайты. Итог — последняя строка `"type":"result"` той
же формы, что `--output-format json`; не-JSON строки (баннер обновления) идут в текст ошибки.
Текст ошибки CLI часто оставляет в stderr, а `result` присылает пустым (так с «No conversation
found» при битом `--resume`) — проверка сброса сессии и лимита смотрит и в stderr.

После выхода процесса stdout и stderr получают `DrainGrace` (5 с) на то, чтобы закончиться, дальше
итог собирается из прочитанного. Фоновый процесс, унаследовавший канал вывода CLI, держит его
конец, пока не завершится сам, и голый `await stdout` повесил бы полосу задач навсегда — таймаут
запуска и `/stop` за выход процесса не дотягиваются (показано подставным CLI: 24 с на
25-секундный фоновый `ping`, теперь 5 с). CLI 2.1.292 при выходе сам завершает то, что его
инструмент Bash запустил через `&`, поэтому живой запуск зависания не воспроизвёл; запас — страховка
для того, что уходит из-под CLI (отделённый `Start-Process`, `start /b` из скрипта, другая версия CLI).
Канал остаётся открытым и читается вхолостую: закрытый, он уронил бы фоновый процесс на
следующей записи.

Каждый `claude` включается в `ClaudeProcessJob` — один Windows Job Object на время жизни шлюза с
`KILL_ON_JOB_CLOSE`. Выход шлюза, в том числе `Stop-Process`, убивает все `claude` и всё, что они
запустили, фоновые dev-серверы тоже; раньше после перезапуска `claude.exe` доделывал задачу, которую
никто не слушает, и писал в сессию, которую продолжит новый экземпляр. Неудачный
`AssignProcessToJobObject` пишется в лог один раз, запуск идёт дальше. Вне Windows ничего не делает —
то же даёт контейнер.

Идущий запуск записан в `state.json` (`GatewayState.ActiveRun`, вопрос — в `ActiveQuestion`:
он идёт параллельно): `ChatWorker` ставит
`BeginRun` перед запуском и `EndRun` в `finally`. Запись на месте при старте — прошлый
экземпляр умер посреди работы: `StartupNotice` шлёт «🔌 Шлюз запущен» всем из
`IChatChannel.AllowedUsers`, в чат прерванного запуска (`ActiveRun.ChatKey` разбирает
`IChatChannel.ParseChat`) — «прерван, напишите „продолжай“», пишет `run.end` с исходом
`interrupted`. Пользователю, который ещё не писал боту, Telegram не даёт отправить первым —
`ChannelFailure.CannotReach` глотается на Debug.

В чате — `RunStatusMessage`: одно сообщение «Работаю…», раз в 4 с редактируется (время,
счётчик вызовов, три последних шага, сабагенты с `↳`). `Report` из потока stdout только
запоминает, сеть — в своём цикле; `DisposeAsync` дожидается цикла (≤10 с), иначе правка
догоняла бы удаление. Аргумент инструмента в статусе один и короткий
(`ClaudeStreamEvent.Describe`): полный ввод Edit/Write — содержимое файла.

## Сессии

Сессии ключуются **нормализованным путём проекта** (`ProjectCatalog.Normalize`): `--resume`
работает только в папке, где сессия создана; смена проекта меняет и активную сессию.
`ChatWorker` фиксирует сессию и `ProjectPath` в `AgentRunRequest` до запуска — иначе
переключение посреди работы развело бы рабочий каталог и проект сессии.

Id новой сессии выдаёт **шлюз** (`NewSessionId` → `--session-id <uuid>`) и регистрирует по
`IAgentRunObserver.SessionStarted` сразу после старта процесса: иначе `/stop`, таймаут или
падение первого запуска теряли бы ветку. Сессия сбрасывается только когда CLI прямо говорит,
что не нашёл её (`LooksLikeMissingSession` → `AgentRunResult.SessionLost`), и только в
`ChatWorker.SettleSession` через `TrySetSessionId(onlyIfActive)` — чтобы не перетереть `/new`
или смену сессии, сделанные во время запуска.

`/sessions` показывает до 8 последних; кнопка несёт `ShortId` (8 символов), а не номер в
списке: завершившийся между отрисовкой и нажатием запуск сдвинул бы номера.

## Контекст: заполненность, разбивка, сжатие

Проверено на CLI 2.1.261.

- **Заполненность.** `usage` в строке `result` — сумма за все ходы, а не размер контекста. Размер —
  это `usage` **последнего** события `assistant` с `parent_tool_use_id: null`:
  `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`. События с
  `"model": "<synthetic>"` — ответы локальных команд с нулями в `usage`, их пропускаем. Окно —
  `modelUsage.<модель>.contextWindow` в итоге (1 000 000 у `sonnet-5`, 200 000 у `haiku-4-5`);
  рядом `canonicalModel` — имя без даты сборки. Алиасы раскрываются в последнюю версию семейства,
  и все получают 1 000 000 без суффикса `[1m]` (CLI 2.1.283): `sonnet` → `claude-sonnet-5`, `opus` →
  `claude-opus-5-5`, `fable` → `claude-fable-5-1`. Поэтому кнопки меню — сами алиасы, и в `--model`
  они уходят как есть: новая версия доходит до чата с обновлением CLI, без релиза шлюза. Версию на
  экранах шлюз берёт из ответа (`state.json`, `ModelVersions`: алиас → `PrimaryModel` того же
  семейства), а до первого ответа — из `ClaudeCapabilities.KnownVersions`. Версия без префикса
  (`/model opus-5-5`, как в подписи) — не алиас:
  `ClaudeCapabilities.CliModel` добавляет ей `claude-`. CLI 2.1.261 молча подменял `fable` на
  `claude-opus-5`; `claude-opus-5-5` требует CLI 2.1.280+. Модель, вышедшую после CLI
  (`claude-sonnet-5-5` на 2.1.283), CLI пропускает с предупреждением `unrecognized_model` в stderr
  и окном 200 000; алиас на неё переводит `ANTHROPIC_DEFAULT_SONNET_MODEL` — см.
  `claude-permissions.md`, «Хуки».
- **Какая модель ответила.** В `modelUsage` основной поток вперемешку с сабагентами и служебными
  вызовами haiku, и сабагент на sonnet часто пишет больше выходных токенов, чем сама сессия. Поэтому
  модель ответа — `message.model` последнего события `assistant` с `parent_tool_use_id: null`, а её
  окно ищется в `modelUsage` по этому имени. Имена расходятся: при `--model claude-opus-5-5[1m]` в
  событии `claude-opus-5-5`, а ключ — `claude-opus-5-5[1m]`; у haiku в ключе дата сборки
  (`claude-haiku-4-5-20251001`). Сравниваются без суффикса `[…]`, префикса `claude-` и даты.
  Проверено на CLI 2.1.283.
- **`/context` в `-p`** работает с `--resume`: модель не вызывается (`num_turns: 0`, пустой
  `modelUsage`), ответ — markdown в `result`: заголовок с `Tokens: 46.6k / 200k (23%)`, таблица
  «Estimated usage by category», а дальше таблицы по каждому MCP-инструменту и скиллу — сотни строк.
  `ClaudeBackend.ContextSummary` отрезает всё после таблицы категорий. Цифры зависят от флагов
  запуска (`--mcp-config`, `--model`), поэтому разбивка идёт с теми же аргументами, что задача.
- **`/compact` в `-p`** работает с `--resume` и сохраняет id сессии. Пишет
  `{"type":"system","subtype":"compact_boundary","compact_metadata":{"pre_tokens":…,"post_tokens":…}}`,
  текст `result` пустой, `num_turns: 0`, но `modelUsage` не пуст — сжатие вызывает модель и тратит
  тариф. После него размер контекста — `post_tokens`, до следующего настоящего хода.
- **Кэш.** Проверено на CLI 2.1.292 через `claude -p --resume`, как запускает шлюз:
  - Основной поток пишет кэш со сроком **один час** (`usage.cache_creation.ephemeral_1h_input_tokens`),
    сабагенты — **пять минут** (`ephemeral_5m`). При оплате сверх подписки основной поток, по описанию
    Claude Code, тоже переходит на 5 минут, поэтому срок читается из события, а не задан заранее.
  - Срок отсчитывается от **начала** запроса, который прочитал или записал кэш; каждое чтение
    бесплатно продлевает его. Поток отдаёт ход только целиком, поэтому началом запроса бэкенд считает
    время последнего ввода основного потока (событие `user` без `parent_tool_use_id` или старт процесса):
    чуть раньше настоящего, и «кэш до» ошибается в безопасную сторону.
    `AgentRunResult.LastRequestUtc` + `CacheTtl` → `SessionRecord.CacheUntilUtc`.
  - Кэш — совпадение начала: инструменты → системный промпт → история. Новый процесс с `--resume`
    его сохраняет. Коммиты, правки файлов, появление `--add-dir`, `--effort` и режимы
    `default`/`acceptEdits`/`auto` тоже. **Сбрасывают:** смена модели (кэш у каждой модели свой, а
    thinking-блоки чужой модели выпадают из истории) и `--permission-mode plan` (другие инструменты —
    не читается ничего). Сжатие заменяет начало сессии, поэтому после него старый кэш не в счёт
    (`LastRequestUtc = null`).
  - Запуск с `--resume <id> --fork-session --no-session-persistence` читает всё закэшированное
    начало, продлевает его ещё на час и не оставляет хода в сессии (проверено на 110 минутах).
- Проверка из Git Bash: MSYS превращает ведущий `/context` в `C:/Program Files/Git/context`, и модель
  получает путь вместо команды. `MSYS_NO_PATHCONV=1` или проверять из PowerShell;
  `ProcessStartInfo.ArgumentList` в шлюзе этого не касается.

## Вопрос без сессии (`Kind = Question`)

`--no-session-persistence` (только с `-p`: в `~/.claude/projects` ничего не пишется, `--resume`
невозможен), без `--resume`/`--session-id`, `--tools WebSearch,WebFetch` (только встроенные; `""`
выключает все) и `--strict-mcp-config`: грузится только свой сервер шлюза `tg` из `--mcp-config` —
иначе MCP-серверы пользователя съедают ~40k токенов контекста на каждый вопрос (48k против 9,6k на
ответе из одного слова). `--permission-mode` и `--permission-prompt-tool` передаются как всегда.
Рабочая папка — пустая `%TEMP%\AgentsTracker-question`: не проект (подтянулся бы его CLAUDE.md) и
не папка данных (секреты).

Вопрос идёт своей полосой `ChatWorker`, **параллельно** задаче: не больше двух процессов `claude`
разом. Права у него прежние — карточки и `send_file` (проверка по проекту чата) работают как раньше;
карточки двух процессов различаются по id запуска в заголовке `X-AgentsTracker-Run` из своего у
каждого запуска файла `--mcp-config` ([architecture.md](architecture.md), «Петля шлюз → CLI →
шлюз»). Инструмента `Agent` в `--tools` нет, так что сабагентов у вопроса не бывает. Ответ, статус и
карточки приходят ответом (reply) на сообщение пользователя.

## Лимиты тарифа

Единственный ограничитель — `IAgentLimits`, окна `five_hour`, `seven_day`,
`seven_day_<модель>`; проверяется в `ChatWorker.ProcessAsync` перед запуском. Остаток одной
строкой — `ShortSummaryAsync` (сводка меню), окна для шкал — `ViewAsync`. `LimitGauge.Used` —
это **израсходованная** доля 0..1 в `decimal`: шкалы `LimitBars` на `/status` и полосы в
мониторе заполняются расходом, полная шкала — окно исчерпано.

Проценты считает **только** `LimitMath` (`Agents.Abstractions`) — единственное правило
округления на весь шлюз: `Percent` — расход вверх до целого с обрезкой в 0..100, `Left` —
`100 - Percent`, а не своё округление. Им пользуются и шкалы в чате, и сводка меню
(`ClaudeLimits.Left`), и `/api/limits`: страница монитора получает `percent` и `left` готовыми,
своей формулы в JS больше нет — в JavaScript нет `decimal`, и та формула расходилась с чатом.
Независимые округления расходились на 14 значениях из 1001: меню показывало «неделя 32%»
против «осталось 33%» в том же `/status`.

`ClaudeLimits` ходит в **недокументированный** `api.anthropic.com/api/oauth/usage` с токеном из
`~/.claude/.credentials.json`: требует правдоподобный User-Agent, отвечает 429 на частый опрос
(кэш 3 мин), может исчезнуть в любой версии — при любой ошибке запуск **пропускается**, не
блокируется, иначе шлюз замолчал бы целиком. Поля читаются через `ClaudeLimits.Number` с
проверкой `ValueKind`: `TryGetDecimal` на `null` бросает, и `utilization: null` уходил бы
пользователю как «Внутренняя ошибка шлюза».

Шкала `utilization` (проценты 0..100 или доля 0..1) выбирается на **весь ответ сразу** —
`ClaudeLimits.LooksLikePercents`: значение от 1 и выше или все значения целые — проценты, только
дробные меньше единицы — доли. По одному окну шкалу не угадать: `utilization: 1` — это и «1% после
сброса», и «выбрано полностью». Пока решение принималось по каждому окну, 10.09.2026 бот час
отказывал на **пустом** пятичасовом окне, показывая сброс нового окна как время ожидания. Ровно
единица уходит в проценты намеренно: в спорном ответе («1» у одного окна и «0.5» у другого) доли
дали бы тот же отказ на пустом окне. Цена: на шкале долей исчерпанное окно запуск не задержит — в
лимит упрётся сам CLI.

Кредиты («extra usage») агенту запрещены: `ClaudeBackend` ставит
`DISABLE_EXTRA_USAGE_COMMAND=1`, при обрыве по лимиту `ChatWorker` снимает всю очередь.

## Скиллы и плагины

`ClaudeSkillCatalog` собирает то же, что видит CLI: `skills/*/SKILL.md` и `commands/**/*.md`
из `.claude` проекта и `~/.claude`, плюс включённые плагины
(`~/.claude/plugins/installed_plugins.json`; `enabledPlugins` наслаиваются профиль →
`.claude/settings.json` → `settings.local.json`, без записи — включён). `user-invocable: false`
не показываются. Обход кэшируется на 5 с: нажатие в меню — это `Apply` и `Render` подряд;
«🔄 Обновить» — `Refresh()`.

Экран «🔌 Плагины» (`ClaudePluginRegistry`) переключает `enabledPlugins[имя@маркетплейс]`
только в личном `~/.claude/settings.json` — туда же пишет `/plugin` самого CLI. Файл
переписывается целиком через `JsonNode` (LF, без `\u`, через временный файл — соседняя сессия
CLI может читать его в этот момент), комментарии не переживут. Значение из слоя проекта
помечено 🔒 и из чата не меняется (`PluginInfo.LockedBy`). Кнопка несёт ключ плагина, а не
желаемое состояние — переворачивается действующее. Действует со следующего `claude -p`.

Встроенные скиллы CLI перечислить нельзя — группа «Встроенные» из
`Gateway:Claude:BuiltInSkills` (дефолт в `ClaudeOptions` под CLI 2.1.x, после обновления CLI —
конфигом без пересборки). «С аргументами» — `SkillLauncher.Expect` запоминает команду за
пользователем, следующий текст `SkillArgumentsTextHandler` превращает в `/команда текст`.
Запуски считаются в `SkillUsage` (суффикс `@бот` отрезается), «⭐ Частые» — до пяти самых
частых.

## Поиск бинарника

`claude.exe` ищет `ClaudeCliLocator`: `Gateway:Claude:Executable` → стандартные пути → PATH →
бинарник расширения VS Code (только чтобы завестись; путь с версией расширения исчезает при
обновлении — пишется предупреждение). Штатно — отдельный CLI
(`irm https://claude.ai/install.ps1 | iex`). Путь кешируется, но перепроверяется перед каждым
запуском. Версию `ValidateStartup` пишет в лог — разбор JSON держится на конкретной версии.
