## 2. Что только в логе, что нигде

Только в логе (после файлового лога станет разбираемо):
- Весь класс «канал недоступен»: Polly `Warning` со стеком на каждую попытку (в смоук-тесте 12 предупреждений на 3 сбоя, плюс `fail` по таймауту polling 2 мин), `ChatGatewayService` «недоступен, попытка N», `TelegramChannel` «Ошибка Telegram polling».
- Потеря части ответа: «Не удалось отправить часть ответа в чат {Chat}» (`ChatWorker.cs:739`) и «Не удалось отправить сообщение» (`:772`).
- Отказ CLI: «claude завершился с кодом N: …» (`ClaudeBackend.cs:513`), «Запуск завершился ошибкой (subtype)».
- Начало каждого запуска с аргументами CLI (`ClaudeBackend.cs:75`) — единственное место, где видны `--resume`/`--session-id`, `--tools`, папка `--add-dir`.
- Отказ в файле (полный путь), лимиты тарифа, прерывание очереди (`DropQueueAsync`).

Ни там ни там не записано:
1. **Ожидание замка папки.** Нет даже строки в логе.
2. **Время между сообщением и стартом запуска** (очередь).
3. **Удаление темы.** Лог Error на каждую попытку, никакого признака «тема мертва», счётчика, пометки в журнале.
4. **Сообщение отброшено ChatWorker при остановке шлюза** (очередь в памяти): `StartupNotice` говорит только про запуск в работе, но не про сообщения в очереди.
5. **Фактический ответ для `error`:** текст ошибки идёт в чат, но не в журнал и не в `RunRecord`.
6. Кто остановил запуск (таймаут, `/stop`, `/stop` из ленты). Исход `cancel` в обоих случаях.

## 4. Файловый лог: проект

Принцип: минимум, по образцу `JsonlAuditLog`. Без NuGet.

### Файл и класс

`src/AgentsTracker.Gateway/Infrastructure/Monitoring/FileLoggerProvider.cs`
(рядом с `RingBufferLog.cs`: оба — приёмники `ILogger`; слой `Infrastructure` не знает фич).

- Папка: `Path.Combine(AppPaths.DataDirectory, "logs")`. Файл: `gateway-ГГГГ-ММ-ДД.log`, день по `DateTimeOffset.Now` (московское время хоста, как в журнале).
- В контейнере `AppPaths.DataDirectory` = `/data` (`Dockerfile:52`), то есть `/data/logs` на томе `data`. Консоль не отключается: `docker logs` остаётся.
- ACL: `DataDirectoryAcl.Restrict` ставит наследуемые права на папку данных. Папка `logs` и файлы под ней унаследуют их; файл, созданный до `Restrict` (первые строки `ValidateStartup`), получит права при пересчёте наследования. Отдельной настройки не нужно.

### Формат

Одна запись — одна строка, продолжение (исключение) с отступом в четыре пробела, чтобы работал `grep`:

```
2026-10-28 12:37:34.276 +03:00 INF ClaudeBackend: claude -p «Создай файл a.txt» …
2026-10-28 12:49:47.274 +03:00 WRN Approvals.OperatorConsole: Отказ в отправке файла …
2026-10-28 12:50:01.100 +03:00 ERR Chat.ChatWorker: Не удалось отправить часть ответа в чат telegram:381305643/452250
    Telegram.Bot.Exceptions.… message thread not found
       at …
```

Поля — те же, что в `LogEntry`: время, уровень, категория (с срезанным префиксом `AgentsTracker.Gateway.`, общая функция с `RingLogger`), сообщение, исключение. Многострочное сообщение: переводы строк в сообщении заменять на `⏎`/пробел с отступом продолжения; тогда одна запись = блок, начинающийся с даты.

Скоуп: `BeginScope` не нужен — ключ чата в тексте сообщений уже есть там, где он важен. Когда добавим ключ запуска, лучше в текст, чем в scope.

### Уровни

- Пол — `Information` (как `RingLogger.IsEnabled`). `Debug` не писать никогда: там сырые payload (`ClaudePermissionTool.cs:35`, `ClaudeBackend.cs:506,514`).
- Фильтры `Logging:LogLevel` из `appsettings.json` действуют поверх (они применяются фабрикой к любому провайдеру): `Polly: Warning` остаётся. Шум Polly — 12 предупреждений со стеком на одну сетевую запинку. Предлагаю не менять: это единственное свидетельство нестабильной сети. Если мешает — `"Polly": "Error"` в `appsettings.json`, но тогда пропадают повторы.

### Запись и сбои

Синхронно, как `JsonlAuditLog`: `lock`, `FileMode.Append`, `FileShare.Read`, `StreamWriter` UTF-8 без BOM, `Flush` на каждую запись. Причина против фоновой очереди (`Channel<T>`): критические строки старта (`LogCritical` при ошибке конфига, `ChatGatewayService.cs:81`) пишутся прямо перед `return 1`/`StopApplication`; фоновый писатель мог бы не успеть сброситься. Объём мал (442 строки за час смоук-теста).

Сбой записи (диск полон, нет прав, файл занят):
1. Исключение не вылетает из `Log` — `try/catch` вокруг всего.
2. В `Console.Error` один раз на серию сбоев. В `ILogger` писать нельзя: рекурсия.
3. Счётчик пропущенных записей; на следующей удачной записи первой строкой: `… WRN FileLog: пропущено N записей лога (причина)`.
4. Папку создаёт `Directory.CreateDirectory` перед каждой записью (дёшево): удалили папку руками — лог поднимется сам.

Защита от разгона: счётчик байтов за сутки (длина файла при первом открытии дня + записанное). Больше 20 МБ в сутки — одна строка «лимит размера, дальнейшие записи дня отброшены» и тишина до следующего дня. Иначе цикл с исключением (polling каждую секунду) съест диск контейнера.

### Хранение

`Gateway:LogRetentionDays`, по умолчанию 14; `0` — файл не писать. Ключ читается в `AddGatewayInfrastructure` через `configuration.GetValue<int?>` (как `McpPort`), без `IOptions`: провайдер создаётся до привязки `GatewayOptions`. Добавить в `GatewayOptions` (проверка: 0..365) и `appsettings.json` по чек-листу `docs/en/extending.md` «a config key».

Очистка: при создании провайдера и при первой записи нового дня — перечислить `gateway-*.log`, дату брать из имени файла (не из времени изменения: восстановление из бэкапа сбросило бы её), удалять старше N суток. Любое исключение при удалении глотается (`IOException`, `UnauthorizedAccessException`) — файл удалится в следующий раз.

### Регистрация

В `GatewayInfrastructure.cs`, рядом со строкой 43:

```csharp
services.AddSingleton<ILoggerProvider>(_ => new FileLoggerProvider(
    Path.Combine(AppPaths.DataDirectory, "logs"),
    configuration.GetValue<int?>($"{GatewayOptions.SectionName}:LogRetentionDays") ?? defaults.LogRetentionDays));
```

`defaults` объявлена ниже в методе — вынести её выше. Порядок провайдеров не важен.
