# План: темы в личке с ботом

Версия 6, 27.10.2026. Минимальный рабочий вариант.

## Требования

1. Тема — способ изолировать сессию внутри диалога с ботом.
2. Каждая тема — отдельная сессия.
3. У каждой темы своя модель, свой effort и свой режим.
4. Тип темы — «проект» или «беседа». Шлюз спрашивает тип в новой теме.
5. Беседа — разговор вне проекта. Модель по умолчанию — модель вопроса (`Gateway:Question`,
   сейчас `sonnet`).
6. Темы работают параллельно.
7. Лента без темы работает как сейчас.

## Решение

1. **Темы — в личке с ботом.** Группа не нужна. Барьер безопасности не меняется: личный чат
   (`ChatKind.Direct`) и `AllowedUsers`. `Telegram.Bot` 22.10.3 (Bot API 10.3) уже знает темы.
2. **Темы создаёте и удаляете вы в клиенте Telegram.** У шлюза нет своих команд для этого.
   Если проба покажет, что пользователь не может создать тему в личке, добавить `/topic new`
   через `createForumTopic`.
3. **Тема — отдельный адрес чата**: `TelegramChatId(long Value, int? Thread)`, ключ
   `telegram:123/42`. Ответы, карточки, файлы, статус и журнал сами идут в свою тему.
4. **У темы своё состояние**: `GatewayState.Topics: chatKey → TopicState`.

   ```
   TopicState { Path?, SessionId?, Model?, Effort?, PermissionMode? }
   ```

   - `Path` — папка проекта. `null` — беседа в папке `%TEMP%\AgentsTracker-talk\<ключ темы>`.
   - Правило ленты «проект из конфига хранится как `null`» к теме не относится. Тема всегда
     хранит путь проекта целиком: `null` у темы значит «беседа».
   - `SessionId` — активная сессия темы. Две темы с одним проектом ведут разные сессии.
   - `Model`, `Effort`, `PermissionMode`: `null` — значение по умолчанию.
     У проекта это конфиг, у беседы — `Gateway:Question`.
5. **Тема без записи** — новая тема.
   - Текст в ней шлюз не запускает и показывает экран «Тип темы?».
   - Команда в ней работает как в беседе: папка беседы чужой проект не трогает.
   - Первая запись (выбор типа, `/project`, `/model` и т. д.) создаёт `TopicState`.
     После `/model` без выбора типа тема — беседа.
6. **`SessionStore.For(chat)`** отдаёт выбор чата: проект, сессию, модель, effort, режим.
   Для темы выбор берётся из `TopicState`, для ленты — из нынешних полей `GatewayState`.
   Вызовы меняются механически: `store.ProjectPath` → `store.For(chat).ProjectPath`.
7. **Очередь задач своя у каждой темы.** Замок на папку пропускает в одну папку только один
   запуск за раз. Так две темы с одним проектом не правят файлы одновременно.
8. **Беседа — запуск с урезанными инструментами**: `--tools WebSearch,WebFetch`,
   `--strict-mcp-config`, режим всегда `default`, без `--add-dir`.
   - Признак — `AgentRunRequest.WebOnly`, а не новый `AgentRunKind`. Тогда `/context` и
     `/compact` в беседе получают те же ограничения.
   - Шлюз очищает папку беседы перед запуском. Проверка доверия к проекту находит пустую
     папку и не показывает карточку.

## Как пользоваться

1. Создайте тему в Telegram и напишите в неё.
2. Шлюз ответит «Тип темы?» и покажет кнопки [📁 Проект] [💬 Беседа]. Задачу шлюз не запустит.
3. Нажмите «Проект» и выберите проект. Или нажмите «Беседа».
4. Пришлите задачу снова.
5. Чтобы сменить проект, модель, effort или режим темы, дайте в ней `/project`, `/model`,
   `/effort` или `/mode`.
6. Чтобы снова выбрать тип темы, дайте `/topic`.

Шлюз не замечает удалённую тему. Её запись остаётся в `state.json` и ничему не мешает.

## Что меняется в коде

Пути — от `src\`. Номера строк — из ревью, `summary.md`.

| Где | Изменение |
| --- | --- |
| `TelegramIds`, `TelegramChannel` | `Thread` в адресе. `ParseChat` понимает `/42` и старые ключи без темы. Тема берётся из `IsTopicMessage ? MessageThreadId : null` во входящем и в нажатии. `messageThreadId` идёт в `SendMessage`, `SendDocument`, `SendPhoto`, `SendChatAction`. `ReplyToMessage` с `MessageId == MessageThreadId` — служебное сообщение темы, его не считать ответом |
| `GatewayState` | + `Topics`. `ActiveRun` → словарь по чату. Старое поле `ActiveRun` читается и переезжает |
| `SessionStore` | + `For(chat)`. Методы сессий (`RegisterSession`, `TrySetSessionId`, `SetSessionId`) и правила «всегда» (`ProjectPathLocked`) получают чат. Активная сессия темы живёт в `TopicState` |
| Вызовы `SessionStore` | около 65 строк в 21 файле |
| `ISettingsScreen` | `RenderAsync`, `RenderFramesAsync`, `Open` получают `ChatId`. Меняются координатор и 9 экранов |
| `ChatWorker` | полоса задач на чат, потребитель создаётся при первой задаче. `IsBusy(chat)` (13 мест), `QueueLength(chat)` (3 места). `DropQueueAsync` отличает полосу вопросов по признаку, а не по ссылке |
| `ChatWorker.Stop(chat)` | в теме — её полоса, её карточки и вопрос, если он из неё. Чат идущего вопроса хранится в полосе. В ленте `/stop` останавливает всё, как сейчас |
| `ChatWorker.ProcessAsync` | модель, effort и режим — из `For(chat)`. Замок на папку берётся сразу после цикла доверия, до модели и лимита. Замок отпускается после `SettleSession` и `RecordRun`, до отправки ответа. Карточка доверия ждёт вне замка |
| Ожидание замка | статус пишет «жду: проект занят». Токен отмены полосы ставится до ожидания, чтобы `/stop` прерывал ожидание |
| `ApprovalBroker` | + `Cancel(chat)`, `HasPending(chat)` через `_runs`, где `RunScope.Chat == chat` |
| `SkillLauncher`, `QuestionLauncher`, `PendingConfirmations` | ключ ожидания `(UserId, ChatId)` |
| `RunMonitor` | у текущего запуска есть владелец. Чужие `Step` и `RunFinished` его не стирают |
| `StartupNotice` | «Шлюз запущен» — один раз в ленту. «Прервано» — в тему запуска, без текста «запущен» |
| `AgentRunRequest`, `ClaudeBackend.BuildArguments` | + `WebOnly`: `--tools WebSearch,WebFetch --strict-mcp-config` у любого вида запуска |
| Беседа в `ChatWorker` | признак беседы определяется по итоговой папке. Папка очищается и создаётся до цикла доверия. Удаление разрешено только внутри корня бесед: нормализованный путь, не равный корню. Режим `default`, `AttachmentsPath: null` |
| `ChatEnqueueTextHandler` | картинка в беседе — отказ до скачивания |
| `Settings` | экран «Тип темы» (`cfg:`), «Проект» ведёт на `ProjectScreen`. Команда `/topic`. Текстовый обработчик «тема без записи → экран» стоит перед `ChatModule` |
| `Help` | `/topic` в справке |

`IChatChannel` не меняется. `ChatDispatcher` меняется только в вызове `SessionStore` для журнала.

## Известные ограничения

- Монитор показывает один запуск — первый из идущих. Очередь в мониторе приблизительная.
  Проект и сессия в мониторе — это выбор ленты.
- Шлюз не ограничивает число параллельных запусков. Окно «5 часов» тратится быстрее.
- Беседа не принимает картинки.
- Позиция в списках меню общая для всех тем (`ScreenNavigation` — по пользователю).
- Замок стоит на папку запуска. Тема на worktree и тема на проекте с сессией в этом worktree
  замок не делят.
- Статус правится раз в 4 с в каждой теме. Предел лички — около 1 сообщения в секунду.
  При трёх и больше запусках возможны ошибки 429. Смоук-тест это проверит.

## Этапы

У каждого коммита есть тег `[topics]`.

1. **Проба** на тестовом боте и на CLI. Проверить:
   - создание и удаление темы в личке на телефоне и на десктопе;
   - ленту без темы и значения `IsTopicMessage` и `MessageThreadId`;
   - отправку, ответ и кнопки в теме;
   - `MessageThreadId` в нажатии кнопки. Если его нет, канал запоминает «сообщение → тема»;
   - `ReplyToMessage` у первого сообщения темы;
   - `--resume` в заново созданной папке беседы.
2. **Адрес темы** в канале. Итог: шлюз отвечает в ту тему, откуда пришло сообщение.
3. **Состояние темы и параллельность**: `Topics`, `For(chat)`, экраны, полосы, замок на
   папку, `/stop` темы, ожидания, `ActiveRun`, монитор. Итог: проекты идут параллельно,
   у каждой темы своя сессия, модель и effort.
4. **«Тип темы» и беседа.**
5. **Смоук-тест**: 2 проекта и беседа параллельно, один проект в двух темах, карточки,
   `/stop` в одной теме, перезапуск шлюза во время запусков.
6. **Документация и слияние.**
   - Глоссарий на двух языках: «тема», «беседа», «тип темы».
   - CLAUDE.md: «два процесса `claude` разом» больше не верно.
   - `docs/en/*.md` и русские зеркала: архитектура, контракт CLI, эксплуатация.
   - Удалить папку `tasks/topics/` перед слиянием в `master`.

## Проверка рядом с боевым шлюзом

На этом ПК работает боевой шлюз — выпуск: MCP на порту `5099`, монитор на порту `5100`.
Пробный экземпляр не должен ему мешать.

1. Не останавливайте боевой шлюз и не собирайте поверх его папки.
2. Соберите пробный экземпляр из worktree в отдельную папку:
   `dotnet build C:\Users\aRRma99\source\repos\ME\AgentsTracker-topics\src\AgentsTracker.Gateway -o $env:TEMP\at-build-topics`.
3. Запустите пробный экземпляр на своих портах: `Gateway__McpPort=5198`, `Gateway__MonitorPort=5199`.
4. Дайте пробному экземпляру свою папку данных:
   `Gateway__DataDirectory=%LOCALAPPDATA%\AgentsTracker-scratch-topics`.
   В ней уже лежит `appsettings.Local.json` с токеном тестового бота и `AllowedUserIds`.
   Задайте ещё `Gateway__ProjectsRoot` — папку с одноразовыми проектами (шаг 6) — и
   `Gateway__ProjectPath` — один из них. Без `ProjectPath` старт не пройдёт проверку.
5. Не давайте пробному экземпляру боевой токен. Боевой токен даст ошибку 409 и сломает опрос
   боевого шлюза.
6. Проверяйте задачи в одноразовых проектах (`git init` в scratchpad). Иначе пробные запуски
   изменят ваши сессии.
7. Не задавайте `/ask` в пробном экземпляре, когда идёт вопрос в боевом шлюзе. Оба экземпляра
   очищают одну папку `%TEMP%\AgentsTracker-question`.
8. Смотрите монитор пробного экземпляра на порту `5199`. Порт `5100` показывает код выпуска.
9. Останавливайте пробный экземпляр по пути exe, а не по имени. Иначе остановится и выпуск.
10. После каждой проверки удаляйте `state.json`, `inbox\` и `audit\` пробного экземпляра.
    `appsettings.Local.json` оставьте до конца задачи.
11. В конце задачи удалите папку данных пробного экземпляра и отзовите токен тестового бота
    в BotFather (`/revoke`).

Рецепт — `docs/en/operations.md`, раздел «Scratch instance».
