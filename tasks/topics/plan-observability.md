# План: журнал и лог

Версия 2, 03.11.2026. Заменяет таблицу B1–B9 в `plan-rework.md`. Сверено с кодом ветки `topics`
(`8926a0f`): три отчёта в `sources/obs-*.md`, главные находки я перепроверил по коду сам.
Номера строк — на этот коммит.

## Зачем

Журнал отвечает «кто, что, когда». Ответить на «почему сломалось» не может ни журнал, ни лог:

1. Лог живёт только в консоли и в 500 строках памяти. Релиз запускает Планировщик, консоли нет:
   после перезапуска не остаётся ничего (`docs/en/deployment.md:235`).
2. `/api/log` монитора отдаёт лог без маски (`RingBufferLog.cs:55-60`). Туда идёт хвост вывода CLI
   (`ClaudeBackend.cs:515, 523`) и тексты исключений. Дыра есть и в `master`.
3. `run.end` — только «время, ходов N» (`ChatWorker.cs:492`). Нет причины ошибки, токенов, модели.
   `cancel` одинаков у `/stop` и таймаута.
4. Потерянный ответ и удалённая тема журнал не видит: `run.end ok`, а в чат ничего не дошло.

## Что изменилось после первого аудита

- **Уже сделано:** чат в записях настроек (`SettingsAudit.cs:10-13`), чат в `session.reset`
  (`ChatWorker.cs:658`), снятие очереди удалённой темы (`ChatWorker.cs:194-200`, пока только лог).
- **Отменено:**
  - `KnownVersions` не трогаем: CLI сам ведёт `sonnet` на `sonnet-5` (`plan-rework.md:75`).
  - Ключ `Gateway:LogRetentionDays` не нужен: константы. Ключ — 6 мест по чек-листу «a config key»
    ради ручки, которую никто не крутит.
  - Код выхода в записи «стоп» бесполезен: в `finally` он всегда 0.
  - Поле `FailureCode` в контракте агента не нужно: subtype и код выхода уже пишет лог
    (`ClaudeBackend.cs:523, 554`). С файловым логом это ищется по времени записи `run.end`.
- **Новые находки:**
  - **Остановка шлюза посреди запуска теряет след.** `finally` снимает запуск из `state.json`
    (`store.EndRun`, `ChatWorker.cs:444`), потом `DeleteQuietlyAsync` на отменённом токене
    пропускает отмену наверх (фильтр `ChatWorker.cs:896`). Итог: `run.start` без `run.end`, при
    старте нет «прервано». На Windows шлюз останавливают `Stop-Process -Force` — `finally` не
    выполняется, путь «прервано» работает. Дыра — в контейнере (`docker stop`) и при Ctrl+C.
    Проверить в харнесе до исправления.
  - **Внутренняя ошибка шлюза не попадает в журнал** (`ChatWorker.cs:202-206`): только лог и
    сообщение в чат. Между `run.start` и `run.end` остаётся `run.start` без пары.
  - **Падение фонового сервиса даёт код выхода 0** (`Program.cs:86`): `ExitCode = 1` ставит только
    отказ подключения (`ChatGatewayService.cs:38`). Планировщик такой выход не перезапустит.
  - **Удалённая тема после запуска:** `SendRenderedAsync` глотает `CannotReach` и пробует все
    оставшиеся части (`ChatWorker.cs:840-845`); очередь темы не снимается.
  - Термина «доставка» нет в глоссарии.

## Решения

| Вопрос | Выбор | Почему не другое |
| --- | --- | --- |
| Файловый лог | свой `FileLoggerProvider`, без NuGet, по образцу `JsonlAuditLog` | перенаправление stdout в Планировщике: нет такой настройки в `<Exec>`, `cmd /c` даёт cp866, без маски и ротации |
| Запись | синхронно, `lock`, `Flush` на каждую строку | фоновая очередь не успеет записать `LogCritical` перед `return 1` |
| Хранение | константы: 14 суток, 20 МБ в сутки | ключ конфига — см. выше |
| Маска | один раз, в приёмниках: общий `LogLine.Format` для кольца и файла | маска в точках вызова — 96 мест, новое забудут |
| Время в консоли | `Logging:Console:FormatterOptions` в `appsettings.json` | свой форматтер консоли не нужен |
| Причина отмены | хост различает сам по токенам | поле в контракте агента не нужно |
| Потеря ответа | новый вид `delivery`, запись только при сбое | outcome у `run.end` подменил бы исход запуска исходом доставки, а перенос `run.end` после отправки вернул бы дыру с остановкой |

## Этапы

Отдельная ветка от `master` после слияния тем. Каждый этап — свой коммит, харнес после каждого.

### 1. Лог в файл и маска (B1, B2, B3)

1. `Infrastructure/Monitoring/LogLine.cs` — `Format(at, level, category, message, exception)`:
   время с поясом, уровень (`INF`/`WRN`/`ERR`/`CRT`), категория без `AgentsTracker.Gateway.`,
   текст через `Text.Redact(Text.Clip(…, 16 КБ))`. Продолжение строки и исключение — с отступом
   в 4 пробела, чтобы одна запись начиналась с даты.
2. `RingLogger.Log` маскирует `Message` и `Exception` той же функцией. JSON `/api/log` не меняется.
3. `Infrastructure/Monitoring/FileLoggerProvider.cs`, около 100 строк:
   - файл `<папка данных>\logs\gateway-ГГГГ-ММ-ДД.log`, UTF-8 без BOM, день по местному времени;
   - пол — Information, Debug не пишется никогда: там сырые карточки и вывод CLI;
   - сбой записи не бросает и не пишет в `ILogger`; один раз на серию — `Console.Error`, потом
     строка «пропущено N записей»;
   - больше 20 МБ за сутки — одна строка «предел размера» и тишина до следующего дня;
   - чистка файлов старше 14 суток по дате в имени, при старте и при смене дня.
   - Регистрация — рядом с `RingBufferLoggerProvider` (`GatewayInfrastructure.cs:43`).
4. `appsettings.json`: `Logging:Console:FormatterOptions` — `SingleLine`, `TimestampFormat`.
5. `ClaudeBackend.cs:515, 523`: `Truncate` → `Text.ClipRedacted`. Это закрывает вывод CLI и в
   консоли, и в `docker logs`: консоль приёмник не маскирует.

Оценка: около 140 строк. Проверка: харнес — маска в кольце и в файле, отсечение Debug, предел
размера, чистка; пробный экземпляр — файл появляется, кириллица читается, формат консоли.

### 2. Сбои процесса (B8)

1. `Program.cs` после `Build()`: `AppDomain.UnhandledException` → `LogCritical`,
   `TaskScheduler.UnobservedTaskException` → `LogError`. Синхронный файловый лог успеет записать.
2. `ChatGatewayService.ExecuteAsync`: исключение из `ListenAsync` — `LogCritical`,
   `Environment.ExitCode = 1`, `StopApplication()`. Тогда Планировщик перезапустит шлюз.

Оценка: около 20 строк.

### 3. Запуск в журнале (B4, B5, B9 и две дыры)

1. **`run.end`** (`ChatWorker.cs:484-492`). Сначала цифры, потом причина — хвост режет предел
   200 знаков:
   - `ok`: `2:14, ходов 5, токенов 12,3 тыс. / 1,8 тыс., opus-5-5`;
   - `error`: те же цифры и `Text.Preview(result.Text, 80)`;
   - `cancel`: те же цифры и причина — `таймаут`, если `runCts` не отменён, `остановка шлюза`, если
     отменён `stoppingToken`, иначе `/stop`.
   - Outcome не меняется: на нём стоит история запусков в мониторе (`index.html:177-181`).
2. **`run.start`**: `ждал N с` от постановки в очередь (поле `QueuedAt` в `QueuedPrompt`,
   `ChatWorker.cs:90, 124`), `замок N с` — вокруг `LockFolderAsync` (`:282`). Оба — только если
   больше секунды. У `/context` и `/compact` — слово «контекст»/«сжатие»: сейчас вид запуска не
   виден нигде.
3. **`limit.refused`** (`:323`): `{модель}: {первая строка отказа}` — в ней уже окно и сброс
   (`ClaudeLimits.cs:86`). Контракт `IAgentLimits` не меняется.
4. **`file.send`** (`OperatorConsole.cs:311`): причина первой, путь вторым —
   `{reason}: {Preview(path, 80)}`.
5. **Внутренняя ошибка** (`ChatWorker.cs:202`): запись `gateway`, `внутренняя ошибка: {тип}:
   {сообщение}`, outcome `error`.
6. **Остановка шлюза посреди запуска:** в `finally` не снимать запуск из `state.json`, если отменён
   `stoppingToken`. Следующий старт сам скажет «прервано» и запишет `run.end interrupted` — путь
   уже есть (`StartupNotice.cs:86-90`). Сначала подтвердить дыру в харнесе: фальшивый канал
   бросает отмену в `DeleteAsync`.

Оценка: около 40 строк.

### 4. Доставка (B6)

1. Глоссарий (оба языка) — до кода: «доставка», «ответ не доставлен».
2. `AuditKinds.Delivery = "delivery"`.
3. `SendRenderedAsync` считает неудачные части и на `CannotReach` бросает дальше: тема удалена,
   остальные части туда тоже не дойдут. `ConsumeAsync` уже снимает очередь такой темы.
4. Записи только при сбое:
   - `partial` — `ответ: не доставлено 2 из 5 частей`;
   - `unreachable` в `ConsumeAsync` — `чат недоступен, снято из очереди: 3`. Покрывает статус,
     карточку доверия и ответ.
5. `SendPlainAsync` не трогаем: «Очередь снята» и «Внутренняя ошибка» остаются в логе.

Оценка: около 20 строк. Это новое поведение: очередь удалённой темы снимается сразу, а не на
следующей задаче. Харнес: сбой части → `delivery partial`; `CannotReach` на ответе → очередь снята.

### 5. Старт и стоп (B7)

1. «старт»: `старт {AppVersion.Current}, {агент} {версия CLI}`, outcome `pid:{pid}`, в контейнере
   `pid:{pid}, container`. Версия CLI уже есть в `RunMonitor.CliVersion`
   (`GatewayInfrastructure.cs:120`) — не запускать `claude --version` третий раз.
2. «стоп»: outcome `stopped` или `error` (из этапа 2).
3. «не запустился»: запись `gateway`, outcome `unauthorized`, когда канал не принял токен
   (`ChatGatewayService.cs:79-85`). Ошибки `ValidateStartup` остаются в логе: журнал ещё не готов.

Оценка: около 12 строк.

## Оценка

Около 230 строк кода и 25 строк документации. Пять коммитов. Этапы 1–2 закрывают дыру в мониторе
и дают «почему» в логе — их можно выпустить отдельно, если нужно быстрее.

## Риски

1. `Redact` маскирует многострочное значение в кавычках только до конца первой строки и может дать
   ложное `***` после `token:` — для лога терпимо (`Text.cs:79, 88`).
2. Консоль и `docker logs` остаются без маски для исключений Telegram. Токен бота в адресе
   исключения не замечен, но гарантии нет. Написать в `safety.md`.
3. «ждал N с» включает карточку доверия: она ждёт человека до 15 минут. Читать вместе с `trust`.
4. Формат `SingleLine` консоли и работу ACL на папке `logs` — проверить на пробном экземпляре.
5. Реакцию Планировщика на код выхода 1 после падения не проверяли — только комментарий в коде и
   `deployment.md:113`.
